# Bridge modules

First-party modules plug into the bridge here. `mod.rs` owns the module
framework (`ModuleDescriptor`, the `BridgeModule` trait, the `ModuleSlots` state
map and the `ModuleHost` enable gate) and the core commands `list_modules` and
`set_enabled_modules`. Each `<id>.rs` is one module's bridge adapter. The design
is in `docs/plans/module-architecture.md`.

## Layers

- `core/modules/<id>/` (crate `bf_<id>`): domain logic. No Tauri, no
  `api-bridge`, no `BridgeState`.
- `src/modules/<id>.rs`: descriptor, state slot, lifecycle hooks and the
  `#[command]`s. Keep commands thin; core code never imports from a module.

## Adding a module adapter

1. Create `<id>.rs` with `pub(crate) const ID`, a `static DESCRIPTOR:
   ModuleDescriptor` (new modules start at `ModuleStage::Experimental`) and a
   `pub(crate) static MODULE` implementing `BridgeModule`.
2. Add `pub(crate) mod <id>;` and `&<id>::MODULE` to `REGISTERED_MODULES` in
   `mod.rs`.
3. Add a `module <id> { ... }` section to `command_list.rs`, in the same order as
   `REGISTERED_MODULES`. New commands are named `<id>_<name>`.
4. Add `"module-<id>"` to `permissions/default.toml`; `build.rs` generates the
   set in `permissions/autogenerated/modules/<id>.toml`.
5. Regenerate and check as in `../../ADDING_COMMANDS.md`.

## State, gate and teardown

- **State slot.** `register_state` inserts one state struct per module
  (`slots.insert(MyState::new())`); there are no module fields on `BridgeState`.
  The slot map is read-only after construction, so the state owns its locks.
- **Gate.** Every command starts with
  `let s = state.modules.enter::<MyState>(ID).await?;` and keeps `s` until it
  returns. Enter once per command. A disabled module returns
  `BridgeError::ModuleDisabled` (code 12001).
- **Lock order.** The gate comes before any module lock. `set_enabled_modules`
  takes the gate's write guard, so it waits for in-flight module commands.
- **`on_disable`.** Runs once when the module is switched off, before any later
  command can enter. Reclaim what the module owns (jobs, GPU leases, layers,
  provider sessions); never call module commands from it. Add other hooks only
  together with the core code that calls them.

## Tests

Put command bodies in plain `async fn`s that take `&ModuleHost`, and have the
`#[command]`s delegate to them. Then test with `ModuleHost::new(&[&MODULE])`,
without Tauri:

- every command rejects with `ModuleDisabled` after `set_enabled(&[])` and works
  again after re-enabling;
- `on_disable` reclaims what the module started;
- domain behaviour lives in the module crate's own tests.

`cargo test -p api-bridge` also checks that every `module` section has a
registered module and that new command names carry the prefix.
