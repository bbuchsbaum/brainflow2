# Module architecture (2026-10-31)

Status: accepted. The owner approved decisions 1–6 on 2026-10-31 (listed at the
end) and asked that modules can be switched off and that the top-level tabs
shown and opened at startup are configurable. Phase A is in progress.

## Goal

Add major features (segmentation, DTI and tractography, angiography and others)
through one well-defined process instead of hand-wiring each one into the shell.
The same process sets the quality bar that decides when a feature has earned a
top-level tab.

Two outcomes define success:

1. A new feature is one folder per layer (Rust crate, bridge adapter, UI module)
   plus one manifest. It does not edit `App.tsx`, `main.rs`, `WorkspaceRouter.tsx`
   or the shared type unions.
2. Every feature passes the same gates on its way from experimental to stable,
   so "rock solid" is a checklist, not a judgement call.

## Where we are

"Plugin" means three different things in the repository today, and only one of
them works:

- **Analysis sidecars** (`analysis.json`, `core/api_bridge/src/analysis.rs`). They
  work, but they are one-shot: stdin is closed after one request, inputs are file
  paths, and the UI polls for status. They cannot add UI. See `plugins/AGENTS.md`.
- **`packages/plugin-sdk`** (BasePlugin, LoaderPlugin, VisualizationPlugin, UIPlugin…).
  It was not imported by `ui2`, any other package or Rust. Removed 2026-10-31.
- **`schemas/0.1.1/brainflow-plugin.json`** with `tools/plugin-verify`. CI compiled
  the schema, but the host never loaded such a manifest. Removed 2026-10-31.

Everything else is first-party code wired by hand. Adding a top-level tab today
touches about eleven places:

1. The `WorkspaceType` union (`ui2/src/types/workspace.ts:18-26`).
2. Five `Record<WorkspaceType, …>` maps: `WORKSPACE_METADATA`,
   `DEFAULT_WORKSPACE_CONFIGS`, `workspaceCounter`, `baseNames` and
   `WORKSPACE_TYPE_TO_MODE`.
3. A second `DisplayMode` union and labels in `ui2/src/hooks/useDisplayMode.ts`.
4. The `WorkspaceRouter.tsx` switch.
5. A `ViewRegistry` factory.
6. An `InspectorRouter.tsx` case.
7. `TOOL_DESTINATIONS` or `DISPLAY_MODES` and the pill order.
8. A native menu item in `src-tauri/src/main.rs` and an arm in
   `navigation_menu_action` (`src-tauri/src/menu_builder.rs`) with tests.
9. A `startup_args.rs` alias.
10. A command-palette entry in the static array in `ui2/src/App.tsx`.
11. A persist-version bump when restore must change.

The other seams are just as manual:

`PlotMode`, `ViewRegistry`, `AnalysisRegistry`, the typed UI `EventBus`) show the
codebase already leans this way. They are filled from static lists.

## Two tiers: modules and providers

Brainflow should support two kinds of extension. They have different trust,
deployment and testing models.

**A module** is first-party, lives in this repository, and is compiled in and
runs in process. It can contribute UI, commands, layer kinds, file formats and
persisted state. It can use core render features. It is enabled or disabled at
runtime and moves through maturity stages. Segmentation, DTI and angiography are
modules.

**A provider** runs out of process. It is discovered at runtime from a plugin
folder and speaks a versioned protocol. It may be third-party, Python, Docker or
a remote server. Modules use providers through typed provider interfaces: for
example an interactive segmentation provider (nnInteractive), a diffusion fit
provider (DIPY, FSL `dtifit`, MRtrix), or a tractography provider. Today's
`analysis.json` sidecar becomes the `job` runner. A new `session` runner adds
long-lived, two-way interaction with pushed events.

**Out of scope for now: in-process third-party UI plugins** (the iframe and
`window.brainflow` idea). The reasons:

- The features worth building need the render loop, the shader contract, GPU
  residency and the coordinate contract. An iframe cannot reach those safely.
- Rust has no stable ABI for loading native code at runtime.
- The design system is enforced by lint in this repo, and third-party UI would
  fragment it.
- "Rock solid" depends on the async-ownership and teardown contracts in
  `AGENTS.md`, which only in-repo code can be held to.

Once the module API has been stable for a while, a sandboxed third tier could be
built on the same contribution points. Nothing below blocks that.

This split matches the tools Brainflow is measured against. 3D Slicer pairs
in-process loadable and scripted modules with out-of-process CLI modules
described by XML. OHIF composes extensions that provide panels, viewports,
toolbars and commands into "modes" that define a workflow. napari's npe2 and
VS Code declare contributions statically in a manifest and load code lazily.

## Anatomy of a module

```text
core/modules/<id>/                    Rust crate bf_<id>: domain logic, no Tauri, transport-neutral
core/api_bridge/src/modules/<id>.rs   Bridge adapter: #[command]s, state slot, events, lifecycle hooks
ui2/src/modules/<id>/
  module.ts                           defineModule({...}): manifest and lazy activate()
  activate.ts                         Registers services, stores and components when first used
  components/  services/  stores/  __tests__/
  AGENTS.md                           Module-specific contracts for agents
docs/modules/<id>/
  proposal.md                         Accepted proposal (template below)
  acceptance.md                       Stage gate evidence
plugins/<provider-id>/                Optional providers the module ships or expects
```

### UI manifest

The manifest is static data, so menus, the palette, shortcuts and settings can
render before the module's code loads. `activate` is a dynamic import, so a
module the user never touches costs no startup time.

```ts
export default defineModule({
  id: 'segmentation',
  title: 'Segmentation',
  version: '0.1.0',
  stage: 'experimental',                       // experimental | preview | stable
  hosts: ['desktop'],                          // desktop | browser
  requires: {
    hostCapabilities: ['nativePaths'],
    renderFeatures: ['subRegionUpload', 'multiOutline', 'zoomPan'],
    modules: [],
  },
  activation: ['onCommand:segmentation.*', 'onViewMode:segmentation.segment'],
  contributes: {
    commands: [{ id: 'segmentation.newSession', title: 'New segmentation on this image', when: 'layer.selected' }],
    keybindings: [{ command: 'segmentation.tool.brush', key: 'b', when: 'viewMode == segmentation.segment' }],
    menus: { 'tools': [{ command: 'segmentation.newSession' }] },
    viewModes: [{ id: 'segmentation.segment', title: 'Segment', layoutPreset: 'segmentation.trace' }],
    inspectorModes: [{ id: 'segmentation.segment', title: 'Segment' }],
    viewportTools: [{ id: 'segmentation.brush', title: 'Brush' }],
    dockTabs: [{ id: 'segmentation.history', title: 'History' }],
    layerKinds: [{ id: 'segmentation.editable-label', base: 'label' }],
    fileFormats: [{ id: 'itksnap-label-table', extensions: ['.txt'], role: 'sidecar' }],
    settings: { brushUnits: { type: 'enum', values: ['mm', 'voxel'], default: 'mm' } },
  },
  activate: () => import('./activate'),
});
```

### Rust side

```rust
pub trait BridgeModule: Send + Sync + 'static {
    fn descriptor(&self) -> &'static ModuleDescriptor;   // id, version, stage, commands, events
    fn on_workspace_reset(&self, ctx: &ModuleCtx) {}
    fn on_volume_released(&self, ctx: &ModuleCtx, volume: &VolumeId) {}
    fn on_disable(&self, ctx: &ModuleCtx) {}             // reclaim leases, layers, providers
}
```

- **State.** Each module owns a state struct registered in a typed slot map on
  `BridgeState` (`state.module::<SegmentationState>()`). No new top-level fields.
- **Commands.** `bridge_commands!` gains named sections, for example
  `module segmentation { segmentation_create_session, segmentation_apply_stroke }`.
  `build.rs` keeps generating permissions per command, plus one permission set per
  module. Command names carry the module id as a prefix, because Tauri command
  names are flat identifiers.
- **Gating.** Compiled modules are always registered and granted, so bindings and
  permissions stay aligned (`pnpm check:permissions:strict`). Runtime enablement is
  enforced inside the adapter: a disabled module's commands return
  `ModuleDisabled`, and its contributions stay hidden in the UI.
- **Generated client.** `packages/api/src/generated/modules/<id>.ts` gives a typed
  client per module. Each module crate exposes one `export_types()` that the
  `export_types` bins call, replacing the hand-maintained lists.
- **Events.** A `bridge_events!` declaration names each event and its ts-rs
  payload type. Module events are namespaced `<id>:<event>`. The generated
  `BridgeEventMap` gives typed `ctx.events.listen()`, which unlistens through
  `safeUnlisten` when the module deactivates.

### The context a module receives

`activate(ctx)` gets the only API a module may use. It lives in
`ui2/src/modules/api/` and is re-exported as `@brainflow/module-api`:

- `ctx.commands`, `ctx.keybindings`: register handlers for the declared ids.
- `ctx.layers`: add, observe and remove layers; read selection.
- `ctx.views`: crosshair, view planes, render requests, viewport tools and overlays.
- `ctx.bridge`: the module's generated client.
- `ctx.events`: typed Rust→UI events and the UI event bus.
- `ctx.state.app(name, { version, migrate })` and `ctx.state.workspace(...)`:
  persisted stores, scoped to the app or to a workspace tab.
- `ctx.settings`: values of the declared settings.
- `ctx.providers`: discover and open provider jobs and sessions.
- `ctx.ownership`: the workspace identity and request-order guards from
  `AGENTS.md`, packaged so stale results are rejected by default.
- `ctx.disposables`: everything registered here is torn down on deactivate.

UI comes only from `components/ui/bf` primitives, which the existing ESLint
ratchet already enforces.

## Contribution points

Each row replaces one of the seams above. "Core-owned" means modules can use the
point but cannot extend it themselves.

| Contribution point | Replaces | Shape | Notes |
|---|---|---|---|

| View modes | Nothing (new) | `{id, title, layoutPreset, inspectorMode, viewportTools, statusItems}` | A mode on a view tab, so a feature keeps slice layouts |

| File formats | `LoaderRegistry` and the UI extension lists | `{id, extensions, sniff, kind, loader, sidecars, writer}` | Rust loaders register from module crates; one generated list replaces the UI copies |
| Settings | `SettingsDialog` sections | Typed schema rendered with bf primitives | Values live in the module's app store |
| Persistence | Independent `persist` keys | `ctx.state.app` and `ctx.state.workspace` with version and migrate | Workspace state rides on the workspace record; disabling a module keeps its data |
| Hover readouts, status items | `HoverInfoService` static list | Existing provider interface | Already a registry |
| Host capabilities | `transport.ts` and `protocol.ts` flags | `hosts` and `requires.hostCapabilities` in the manifest | Unsupported contributions are hidden, never mocked as success |
| Render features | Core-owned | Named features advertised by `get_render_capabilities` | Modules declare what they need; see the next section |
| Providers | `analysis.json` only | Provider kinds with typed interfaces; `job` and `session` runners | Capability consent and a licence field per provider |

## Core-owned capabilities

Anything that touches the shader contract, `BridgeState` lifetimes, the
coordinate contract or GPU residency stays in core. A module declares the core
features it needs, and missing features are built in core first, with their own
contract tests. This is the main way the module process protects the renderer.

Laying the three example modules side by side shows most of the core work is
shared:

| Core capability | Segmentation | DTI and tractography | Angiography | Today |
|---|---|---|---|---|
| Sub-region texture upload, revision keys | Brush strokes | Not needed | Vessel edits | Whole-volume upload only |
| Zoom and pan; native and oblique planes | Tracing | Inspecting tracts | Vessel planes | Three world-aligned view types; no zoom |
| Several outline layers per frame | Active label plus reference | Not needed | Lumen and wall | One outline layer |
| Compute tier (WGSL compute, CPU derived volumes) | Filters, GrowCut | FA and MD if computed in app | Vesselness (Frangi) | None |
| Multi-channel volumes (RGB, vector, tensor) | Not needed | DEC-FA, principal directions, tensors | Not needed | R8, R16F and R32F scalars only; the NIfTI loader rejects 5D |
| Line geometry in slices and 3D | Not needed | Streamlines | Centrelines | None |
| Slab projection (MIP, MinIP, thick slab) | Not needed | Not needed | Core view | None; `max` blending is between layers |
| Volume ray-marching | Mesh preview | Context rendering | 3D vessel view | None |
| Editable label store and label writer | Core of the module | ROIs and seeds | Vessel masks | None |
| Session provider runner | AI prompts | Interactive tractography | Vessel AI | One-shot jobs only |

Each capability is delivered once and then serves every module that asks for it.
The order of core work should follow the order of modules.

## The process

1. **Proposal.** Write `docs/modules/<id>/proposal.md` from the template:
   - the workflow it serves and how that connects to `docs/vision.md` ("add a
     new feature when its place in the workflow is clear");
   - who uses it and what they do today instead;
   - its contribution list;
   - core capabilities it needs, and which are missing;
   - providers and their licences;
   - data contracts: formats, coordinates, units, precision;
   - performance budgets on named reference data;
   - risks and the acceptance plan.

   The owner accepts or rejects it.
2. **Core first.** Each missing core capability lands as its own change with
   contract tests and GPU tests that never soft-skip. Modules never patch shaders,
   `BridgeState` or coordinate code.
3. **Scaffold.** `cargo xtask new-module <id>` creates the crate, the bridge
   adapter, the UI folder with `defineModule`, test stubs, `AGENTS.md` and the
   acceptance checklist. It also registers the module in
   `core/api_bridge/src/modules/mod.rs` and `ui2/src/modules/index.ts`.
4. **Build at `experimental`.**
5. **Promote** through the stage gates below, recording evidence in
   `docs/modules/<id>/acceptance.md`.
6. **Retire** when needed: stage `retired`, persisted state migrated or exported,
   contributions removed.

`pnpm check:modules` verifies, in CI:
- that UI manifests and Rust descriptors list the same modules and commands;
- that every module command has a permission and a dev-harness handler;
- that contribution ids are namespaced and unique;
- that keybindings don't conflict within a scope;
- that each module has an `AGENTS.md` and an acceptance file matching its stage.

## Maturity stages

| Stage | Visibility | Gate to enter |
|---|---|---|
| Experimental | Off by default; one switch per module in Settings › Experimental features | Accepted proposal; builds; contributions hidden when off |
| Preview | On, labelled "Preview"; reachable from the command palette, the Tools menu and view modes. No top-level tab or pill, no global shortcuts | Experimental gate below |
| Stable | May own a top-level tab or pill and global shortcuts | Preview gate below, plus owner sign-off |

**Experimental → preview:**
- Unit and bridge tests for every command; `pnpm check:permissions:strict` and
  `pnpm check:modules` pass.
- Dev-harness handlers for every command, and at least one harness scenario.
- A teardown test: entering and leaving the module, closing its tab and unloading
  its inputs leaves no layers, GPU slots, listeners, provider sessions or cached
  samplers behind.
- A stale-result test for every asynchronous command.
- Persistence round-trip and migration tests if the module persists anything.
- Lint ratchet clean; no raw palette classes or hex.

**Preview → stable ("rock solid"):**
- An e2e harness scenario with visual baselines.
- A native acceptance run on macOS, Windows and Linux, in the style of
  `docs/alpha-acceptance.md`, including GPU and visual checks.
- Performance budgets from the proposal measured on reference data, with
  results recorded.
- Crash recovery for modules that edit data (journal or autosave), tested by
  killing the app mid-edit.
- Every failure has a designed state; nothing fails silently.
- User documentation and a reviewed keyboard map.
- One release cycle in preview with no open P1 issues.

A top-level tab is therefore earned, not assumed. A module can be very useful at
preview through view modes and the Tools menu.

## Switching modules off and configuring the top bar

Stage decides what a module may claim. The user decides what they see:

- **Settings › Modules** lists every module with an on/off switch, at every
  stage. Experimental modules default to off; preview and stable modules default
  to on. A module that is off is not activated, contributes no tabs, menu items,
  commands, shortcuts or settings, and its bridge commands reject. Its saved data
  is kept, so switching it back on restores it.
- **Settings › Top bar** chooses which tool tabs appear in the Tools menu and
  which are pinned in the top bar, and which tabs open at startup. The default is
  today's behaviour: relaunch restores the tabs the user had open
  (`docs/plans/qa-design-decisions-2026-10-30.md` §1). The alternative is a fixed
  list, for example one Orthogonal view and Segment.
- A module's manifest only proposes defaults (`pinned`, `openAtStartup`). The
  user's settings always win, and a module never adds itself to the top bar once
  the user has removed it.
- Restore skips tabs whose module is off, and brings them back when it is
  switched on again.

## The three example modules

**Segmentation** (research: `docs/plans/segmentation-module-research.md`):
- *Contributions:*
  - a `segment` view mode with a Trace layout preset;
  - a Segment inspector mode that replaces the Annotate stub;
  - brush, contour and fill viewport tools;
  - an editable label layer kind;
  - label writers and label tables (ITK-SNAP, FreeSurfer, BIDS `dseg.tsv`);
  - keymap presets;
  - history and statistics dock tabs;
  - an interactive segmentation provider for nnInteractive, using the session runner.
- *Core capabilities:* sub-region upload, zoom and pan, oblique planes, several
  outline layers, the compute tier, and the editable label store.
- *Top-level placement once stable:* a "Segment" tool entry that opens a view tab
  in the Trace layout with Segment mode on. This keeps the 2026-10-30 rule that a
  tool opens its own tab and is refocused on reopen, while keeping slice layouts,
  which tool tabs lack today.

**DTI and tractography:**
- *Contributions:*
  - file formats: `bvec`/`bval` sidecars, 4D DWI, tensor NIfTI (5D), and

  - layer kinds: DEC-FA colour, principal-direction glyphs, streamlines;
  - providers: tensor and model fitting, and tractography (DIPY, FSL or MRtrix
    as jobs; seeded tracking as a session);
  - inspector sections for scalar maps and tract selection;
  - a tract-profile plot mode.
- *Core capabilities:* multi-channel volumes, a 5D NIfTI path, line geometry in
  slices and 3D, oblique planes.

**Angiography:**
- *Contributions:*
  - slab MIP and MinIP controls on view tabs;
  - a vesselness filter;
  - centreline extraction as a provider;
  - diameter and stenosis measurement tools;
  - a 3D vessel view.

  It can declare an optional dependency on the segmentation module for vessel

- *Core capabilities:* slab projection, the compute tier, line geometry,

## Delivering the architecture

Build the architecture by moving existing features onto it first. That proves the
API before a new module depends on it, and it shrinks `App.tsx` and `main.rs`.

| Phase | Ships | Exit evidence |
|---|---|---|
| A. Registry skeleton | `ui2/src/modules/` registry with commands, keybindings, palette, menus, workspaces, inspector modes, dock tabs and settings. Settings › Modules switches and Settings › Top bar (pinned tools, startup tabs). Rust `BridgeModule`, the state slot map, named `bridge_commands!` sections, per-module permission sets and generated clients. **Port the Analysis workbench** (tool tab, four commands, sidecar runner) as the first module | The Analysis workbench is defined entirely by its module: no edits to `App.tsx`, `main.rs`, `WorkspaceRouter.tsx` or `types/workspace.ts` remain. Existing tests and harness scenarios still pass |
| B. Data and render seams | An open loader registry used by the load path; a file-format registry with one generated extension list; layer-kind descriptors; the typed event registry; workspace-scoped persistence; host-capability declarations; `get_render_capabilities` | A test format (for example `.tck` loaded as metadata only) added with no edits outside its module |
| C. Process tooling | `cargo xtask new-module`; proposal and acceptance templates; `pnpm check:modules` in CI; stage switches in Settings | A scaffolded empty module passes CI unchanged |
| D. Provider protocol v2 | `job` and `session` runners, pushed events, capability consent, licence field, raw-byte inputs; `analysis.json` migrated to `runner.type = "job"` | The bundled example sidecar runs unchanged; a mock session provider passes stale-response and teardown tests |

Segmentation can start once Phase A lands. Its own phase 0 (the editable label
store, sub-region upload, zoom and pan) is core work that overlaps Phase B. BIDS
explorer and Set studio can move onto the registry after the Analysis workbench,
when convenient.

## Guardrails

- **Boundaries are enforced.** ESLint `no-restricted-imports` lets modules import
  only `@brainflow/module-api`, `components/ui/bf` and their own folder. Core code
  never imports from a module. Module crates do not depend on `api_bridge` or
  Tauri; the adapter file is the only glue.
- **Namespaced ids.** Every contribution id is `<module>.<name>`. The registry
  rejects duplicates at startup.
- **A disabled module costs nothing.** It is not activated, holds no listeners,
  and its commands reject.
- **Provenance.** Layers and files a module produces record the module id and
  version, and the provider and model licence when one was used.
- **No compensating geometry.** Modules use the shared `SliceViewport` geometry
  and the coordinate contract; they never add their own flips or reflections.

## Decisions (approved 2026-10-31)

The owner approved the recommendation in each item below.

1. **Third-party scope.** Recommended: providers only for now; revisit
   in-process UI plugins after the module API has been stable.
2. **Menu strategy.** Recommended: the UI sends a menu model to Rust, which keeps
   predefined items, accelerators and the `menu_builder.rs` tests. The
   alternative is building the whole menu with the Tauri JS menu API
   (`core:menu:default` is already granted).
3. **Segmentation's top-level entry once stable.** Recommended: a Segment tool
   entry that opens a Trace-layout view tab. The alternatives are a layout pill
   or a mode only.
4. **Port existing tools.** Recommended: the Analysis workbench in Phase A; BIDS
   and Set studio later.
5. **Names.** "Module" for first-party features, "provider" for out-of-process
   extensions. Keep `plugins/` as the provider folder.
6. **Retire the unused plugin scaffolding.** `packages/plugin-sdk`,
   `schemas/0.1.1/brainflow-plugin.json` and `tools/plugin-verify` describe a
   system that was never built. Recommended: remove them, or rework the schema
   into the provider manifest schema in Phase D.
